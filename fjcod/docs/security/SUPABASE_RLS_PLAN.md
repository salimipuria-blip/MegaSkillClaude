# طرح احراز هویت و RLS برای CHAM روی Supabase

**وضعیت: baseline schema/RLS و migration اجرایی برای بازبینی در مخزن آماده است؛ روی هیچ دیتابیسی اعمال یا برای production تأیید نشده است.**

نسخهٔ فعلی CHAM یک برنامهٔ محلی است: داده‌ها در `localStorage` نگه‌داری می‌شوند، ورود در مرورگر انجام می‌شود و مجوزهای نقش را سرور enforce نمی‌کند. تغییر شناسهٔ session فقط جلوی یک جعل سادهٔ نشست را می‌گیرد؛ محرمانگی یا تمامیت دادهٔ محلی را تضمین نمی‌کند. تا تکمیل مهاجرت و تست RLS، دادهٔ واقعی مالی یا اطلاعات حساس مشتری وارد نکنید.

## موارد لازم پیش از اعمال روی دیتابیس

Baseline مخزن طبق تصمیم این نوبت یک فروشگاهِ فعلی با جداسازی `store_id`، ماتریس نقش‌های زیر، حساب FJCOD جدا از مالک فروشگاه، و دامنهٔ صرفاً schema/RLS است؛ seed و انتقال داده جزو این migration نیستند. این انتخاب‌ها اجازهٔ اجرای زنده یا production approval محسوب نمی‌شوند.

1. پروژهٔ Supabase مقصد، منطقه، مالکیت حساب و روش نگه‌داری backup مشخص شود.
2. برای هر کاربر، حساب واقعی `auth.users.id` و عضویت اولیه به‌صورت امن تعیین شود. رمزهای نمونه و هش‌های محلی هرگز به Supabase Auth منتقل نشوند؛ برای همهٔ افراد دعوت/بازیابی رمز امن انجام شود.
3. مالک کسب‌وکار ماتریس دسترسیِ مشاور به اطلاعات تماس مشتری، دیدن فروش دیگران، مرجوعی، تخفیف و اصلاح موجودی را برای بهره‌برداری واقعی کتبی تأیید کند.
4. نام و ساختار جدول‌ها، قیود یکتا، ارز/واحد مبلغ، منطقهٔ زمانی، سیاست نگه‌داری audit، و مرجع واحد شمارهٔ فاکتور بازبینی شوند.

تا تکمیل این موارد و بازبینی روی پروژهٔ disposable، هیچ SQL را روی Supabase زنده اعمال نکنید.

## مدل پیشنهادی هویت و tenant

- Supabase Auth تنها منبع هویت است؛ تمام تصمیم‌ها از `auth.uid()` و عضویت فعال در فروشگاه استخراج شوند.
- **نقش `owner` فعلی در `fjcod/src/core/seed.ts` به حساب FJCOD/مالک سیستم اشاره دارد، نه مالک فروشگاه چام.** این نقش را به `store_owner` تبدیل یا خودکار نگاشت نکنید. مالک فروشگاه، مدیر فروشگاه و دسترسی پشتیبانی FJCOD باید هویت‌ها و مرز جداگانه داشته باشند؛ دسترسی پشتیبانی پیش‌فرض و دائمی نباشد.
- جدول عضویت پیشنهادی: `public.cham_memberships(user_id, store_id, role, active, created_at)`. قید یکتا روی `(user_id, store_id)` و FK روی Auth user و فروشگاه لازم است.
- نقش از body درخواست، `user_metadata`، localStorage یا مقدار انتخاب‌شده در UI پذیرفته نشود. `app_metadata` نیز فقط در صورتی قابل اتکاست که فقط سرور قادر به تغییر آن باشد؛ عضویت DB مرجع ترجیحی است.
- همهٔ ردیف‌های متعلق به فروشگاه `store_id NOT NULL` داشته باشند. درج/به‌روزرسانی باید عضویت فعال در همان فروشگاه را در `WITH CHECK` اثبات کند؛ تغییر tenant ID توسط کاربر ممنوع باشد.
- `anon` هیچ دسترسی به دادهٔ تجاری نداشته باشد. دسترسی‌های `authenticated` به‌صورت حداقلی اعطا شوند و RLS روی تمام جدول‌های Data API فعال باشد.

## ماتریس اولیهٔ دسترسی (نیازمند تأیید مالک)

نقش‌های عملیاتی از `fjcod/src/core/types.ts` الهام گرفته‌اند، اما این جدول mapping نهایی نیست؛ به‌خصوص `owner` محلی معادل `store_owner` نیست.

| داده/عملیات | مالک فروشگاه (نقش جدید) / مدیر | معاون | صندوقدار | مشاور فروش |
|---|---|---|---|---|
| فهرست کالا | خواندن/نوشتن | خواندن/نوشتن | خواندن | خواندن |
| مشتریان | خواندن/نوشتن؛ خروجی ممیزی | خواندن/نوشتن | حداقل اطلاعات لازم برای فروش | دسترسی حداقلی؛ جزئیات PII نیازمند تصمیم |
| فروش و مرجوعی | دیدن فروشگاه؛ مرجوعی با RPC مجاز | دیدن فروشگاه؛ مرجوعی با RPC مجاز | ایجاد از RPC؛ دیدن فروش خود | فقط سبد/فروش منتسب به خود |
| موجودی و گردش کالا | خواندن؛ اصلاح از RPC | خواندن؛ اصلاح از RPC | بدون اصلاح مستقیم | بدون اصلاح مستقیم |
| شیفت | همهٔ شیفت‌ها | همهٔ شیفت‌ها | فقط شیفت خود | ندارد |
| کاربران، تنظیمات، مجوز | مدیریت بر اساس اختیار سروری | اختیار محدود و تأییدشده | ندارد | ندارد |
| audit | خواندن؛ ثبت غیرقابل‌ویرایش | خواندن محدود | بدون حذف/ویرایش | بدون حذف/ویرایش |

پیشنهاد پیش‌فرض: امتیاز، نرخ پورسانت، قیمت تمام‌شده، رمز/توکن، جزئیات پشتیبان و لاگ‌های احراز هویت هرگز به نقش‌های پایین‌تر فرستاده نشوند، مگر نیاز کاری و مجوز جداگانه تعریف شود.

## الگوی پیاده‌سازی RLS

1. سیاست‌ها را با **deny-by-default** شروع کنید. برای هر جدول عملیات `SELECT`, `INSERT`, `UPDATE`, `DELETE` جداگانه بررسی شود؛ داشتن policy خواندن به‌معنی مجازبودن نوشتن نیست.
2. تابع کمکی عضویت، در صورت نیاز، در schema غیرقابل‌نمایش در Data API قرار گیرد؛ با `SECURITY DEFINER`, `SET search_path = ''`, نام‌گذاری schema-qualified و استفاده از `auth.uid()`. اجرای تابع برای `PUBLIC` و `anon` لغو و فقط برای نقش‌های لازم اعطا شود. اگر ارزیابی policy به `USAGE` روی schema نیاز داشت، فقط همان مجوز لازم اعطا شود؛ دسترسی به جدول‌ها باز نشود و schema از فهرست schemaهای exposed خارج بماند. از بازگشت policy به خود جدول عضویت (RLS recursion) پرهیز شود.
3. هر policy برای تغییر ردیف هم `USING` و هم `WITH CHECK` مناسب داشته باشد. نقش/فروشگاه پیش از هر نوشتن از عضویت معتبر DB به دست آید.
4. فروش، مرجوعی، مصرف/بازگشت موجودی و ثبت پرداخت باید در RPC تراکنشی سمت سرور انجام شوند. RPC قیمت، تخفیف، مالیات، مجموع، موجودی، شمارهٔ فاکتور و مالکیت فروش را خودش محاسبه/اعتبارسنجی کند؛ مقادیر محاسبه‌شدهٔ کلاینت معتبر نیستند.
5. RPCهای `SECURITY DEFINER` باید ورودی‌ها را محدود کنند، `search_path` خالی داشته باشند، مجوز اجرا را صریح کنند، از شناسهٔ کاربر ارسالی اعتماد نگیرند و هیچ خطای داخلی/secret را به کلاینت ندهند.
6. سرویس‌روِل فقط در محیط سرور/Edge Function استفاده شود؛ هرگز در Vite، مرورگر، `localStorage`، log یا فایل‌های commit‌شده قرار نگیرد. Endpoint سروری علاوه بر `verify_jwt`، نقش و عضویت را خودش بررسی کند.
7. audit append-only باشد: نوشتن فقط از RPC/سرور؛ حذف و ویرایش مستقیم برای کاربران عادی ممنوع. اطلاعات اضافی و PII در جزئیات audit ثبت نشود.

## طرح آزمون اجباری پیش از استفادهٔ واقعی

- کاربر بدون نشست، `anon`, نشست منقضی، عضویت غیرفعال و کاربر حذف‌شده هیچ دادهٔ تجاری نبیند.
- کاربر فروشگاه A با تغییر `store_id`, شناسهٔ کالا/مشتری/فاکتور یا payload نتواند به فروشگاه B بخواند یا بنویسد.
- نقش مشاور/صندوقدار نتواند فروش دیگران، قیمت تمام‌شده، تنظیمات یا audit غیرمجاز را بخواند.
- client نتواند خودش را owner/manager کند، عضویت بسازد، مبلغ نهایی یا موجودی را جعل کند، یا RPC مرجوعی/تخفیف غیرمجاز فراخوانی کند.
- دو checkout هم‌زمان نتوانند موجودی منفی یا شمارهٔ فاکتور تکراری بسازند؛ خطای پرداخت/ثبت باعث rollback کامل شود.
- بازیابی backup روی پروژهٔ آزمایشی، مهاجرت نسخه‌های فعلی و لغو نشست‌ها تمرین شود. آزمون‌ها با fixture دادهٔ ساختگی و پروژهٔ staging انجام شوند.

## انتشار و بازگشت

- ابتدا از هر دستگاه دادهٔ CHAM صادر و hash/تعداد ردیف‌ها جداگانه ثبت شود؛ هیچ دادهٔ مرورگر خودکار پاک یا overwrite نشود.
- طرح نهایی با backup تازه روی Supabase آزمایشی اجرا، RLS linter و تست‌های منفی بررسی شود؛ سپس مالک دربارهٔ زمان توقف فروش تصمیم بگیرد.
- قبل از rollout، مسیر dual-read/write و reconciliation یا برنامهٔ توقف/بازگشت تعیین شود. به‌روزرسانی schema تنها با migration شماره‌دار و بازبینی‌شده انجام شود.
- پس از rollout، حساب آزمایشی هر نقش، دو فروشگاه آزمایشی، audit، backup restore، خروج/ابطال نشست و پایش خطا آزموده شود.
- بازگشت باید کد برنامه را به نسخهٔ قبل برگرداند و backup دیتابیس را بازیابی کند؛ migration مخرب یا حذف داده بدون backup قابل‌بازیابی ممنوع است.

## Migration اولیهٔ آماده‌شده

فایل اجرایی [`20261014000000_cham_schema_rls.sql`](../../supabase/migrations/20261014000000_cham_schema_rls.sql) جدول‌های اولیه، کلیدهای tenant، helperهای کم‌دسترسی و policyهای RLS را می‌سازد. این migration **فقط schema/RLS** است: هیچ ردیف فروشگاهی، عضویت، دادهٔ نمونه یا دادهٔ localStorage وارد نمی‌کند و RPC تراکنشی فروش/مرجوعی هم ندارد؛ به همین دلیل هنوز backend قابل‌استفادهٔ برنامه نیست. سیاست‌ها تا زمان ایجاد membership با دسترسی پیش‌فرض بسته می‌مانند.

`fjcod/supabase/config.toml` فقط شناسهٔ محلی Supabase و schemaهای مجاز API را تنظیم می‌کند؛ پروژهٔ remote را link نمی‌کند و credential ندارد. migration در این نوبت به هیچ دیتابیسی اعمال نشده است. پیش از `db reset`/`db push` باید فایل را روی پروژهٔ disposable بررسی، migration و policyها با تست‌های منفی اجرا، backup و نگاشت کاربران تأیید، و روش bootstrap اولین مالک تعیین شود.

حساب FJCOD به‌عنوان platform operator جدا نگه داشته شده؛ جدول ثبت اپراتورها خالی و غیرقابل‌دسترسی برای نقش‌های مرورگر است. هیچ دسترسی دائمی یا مسیر پشتیبانی به دادهٔ فروشگاه ایجاد نشده؛ workflow دسترسی موقت نیازمند migration و بازبینی جداگانه است.
