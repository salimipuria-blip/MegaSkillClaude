# pro-backend-api-design

## هدف
APIای که قراردادش روشن است، ورودی بد را رد می‌کند، دوبار اجرا شدن خرابش نمی‌کند و بدون قطعی تغییر می‌کند.

## چه زمانی فعال شود
ساخت endpoint، طراحی دیتابیس، اتصال درگاه پرداخت، webhook، یا وقتی API کند/ناپایدار است.

## گردش کار
1. **قرارداد اول**: منابع، مسیرها، بدنهٔ درخواست/پاسخ و کدهای وضعیت را قبل از کد بنویس (OpenAPI یا نوع‌های TypeScript/zod مشترک).
2. **اعتبارسنجی در مرز**: هر ورودی (body، query، header، webhook) با schema اعتبارسنجی شود؛ فیلد ناشناخته رد شود.
3. **خطای یکدست**: قالب ثابت `{ "error": { "code": "CART_EMPTY", "message": "…" } }`؛ 400 ورودی بد، 401 بدون هویت، 403 بدون مجوز، 404، 409 تعارض، 422 قانون کسب‌وکار، 429، 5xx فقط برای خطای سرور. جزئیات داخلی و stack به کلاینت نرود.
4. **Authn ≠ Authz**: هر endpoint بررسی کند «این کاربر اجازهٔ این منبع خاص را دارد؟» (مالکیت/نقش)، نه فقط «لاگین است؟». در Supabase از RLS استفاده کن.
5. **Idempotency**: عملیات پولی و webhook با `Idempotency-Key` یا کلید یکتای رویداد؛ اجرای دوباره نتیجهٔ قبلی را برگرداند.
6. **دیتابیس**: کلید و ایندکس برای هر کوئری پرتکرار؛ تراکنش برای تغییرات چندجدولی؛ مبلغ پول با integer (ریال/تومان) نه float؛ زمان UTC و تبدیل جلالی فقط در نمایش.
7. **Migration امن**: expand → backfill → contract؛ هرگز ستون در حال استفاده را در یک مرحله حذف/تغییرنام نکن.
8. **قابلیت مشاهده**: لاگ ساخت‌یافته با request-id، بدون داده‌ی حساس؛ health endpoint؛ timeout و retry با backoff برای فراخوانی خارجی.
9. **صفحه‌بندی و محدودیت**: cursor pagination برای لیست‌ها، rate limit برای endpointهای عمومی.

## چک‌لیست کیفیت
- [ ] هر endpoint: schema ورودی، کدهای خطا و بررسی مجوز دارد
- [ ] عملیات پولی/webhook idempotent است و تست تکرار دارد
- [ ] migration برگشت‌پذیر یا مرحله‌ای است
- [ ] هیچ راز یا داده‌ی شخصی در لاگ/پاسخ خطا نیست
- [ ] تست integration برای مسیر موفق و حداقل دو مسیر خطا

## خروجی
قرارداد API + schema دیتابیس و migration + کد handlerها با اعتبارسنجی/مجوز + تست‌ها + نکات استقرار.
