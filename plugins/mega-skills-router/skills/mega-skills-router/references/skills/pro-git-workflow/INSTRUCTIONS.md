# pro-git-workflow

## هدف
تاریخچه‌ای که خواندنی و قابل‌برگشت است، و تغییراتی که بدون ترس merge و منتشر می‌شوند.

## چه زمانی فعال شود
commit، PR، merge conflict، انتشار نسخه، «کدم رو خراب کردم برگردونم»، یا راه‌اندازی CI.

## گردش کار
1. **شاخه برای هر کار**: از آخرین `main` (`git fetch origin main && git switch -c feat/…`)؛ یک هدف در هر شاخه.
2. **commit اتمی و معنادار**: هر commit یک تغییر منطقی که build را نمی‌شکند. پیام: خط اول ≤ ۷۲ کاراکتر به سبک Conventional Commits (`fix(cart): …`)، بدنه = **چرا**، نه چه.
3. **قبل از push**: lint، typecheck و تست‌های بخش تغییرکرده محلی اجرا شوند؛ `git diff --staged` را خودت بخوان؛ هیچ راز یا فایل build در stage نباشد.
4. **PR کوچک**: زیر ~۴۰۰ خط تغییر؛ توضیح: چه، چرا، چطور تست شد، ریسک و راه برگشت. پیش‌نویس تا CI سبز شود.
5. **حل تعارض**: base را به شاخه merge کن (روی شاخه‌ی مشترک rebase/force-push نکن)؛ هر تعارض را با فهم هر دو طرف حل کن؛ lockfile را با ابزار خودش دوباره بساز، نه دستی؛ بعد تست‌ها را دوباره اجرا کن.
6. **CI قرمز**: اول ریشه‌یابی؛ «flaky» فقط با شاهد. هرگز تست را skip نکن تا سبز شود.
7. **انتشار**: نسخه‌دهی معنایی (MAJOR.MINOR.PATCH)، tag و یادداشت انتشار؛ انتشار تدریجی یا feature flag برای تغییرات پرریسک.
8. **برگشت**: `git revert <sha>` روی main (تاریخچه را بازنویسی نکن)؛ برای کار گم‌شده `git reflog`.

## ضدالگوها
- commitهای «fix»، «wip»، «update» بدون توضیح.
- PR غول‌پیکر که چند هدف را مخلوط کرده.
- `git push --force` روی شاخه‌ای که دیگران هم استفاده می‌کنند.

## چک‌لیست کیفیت
- [ ] هر commit پیام معنادار با «چرا» دارد
- [ ] تست و lint قبل از push محلی سبز شده
- [ ] PR توضیح تست و راه برگشت دارد
- [ ] هیچ راز، فایل build یا تغییر بی‌ربط در diff نیست

## خروجی
دستورهای دقیق Git برای همان موقعیت + پیام commit/توضیح PR آماده + برنامهٔ انتشار یا برگشت.
