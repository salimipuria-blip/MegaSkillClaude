# pro-testing-strategy

## هدف
تست‌هایی که **باگ واقعی را می‌گیرند** و سریع و پایدارند — نه درصد پوشش تزئینی.

## چه زمانی فعال شود
«تست بنویس»، «coverage پایینه»، «CI گاهی قرمز می‌شه»، قبل از refactor بزرگ، یا شروع پروژهٔ جدید.

## گردش کار
1. **نقشهٔ ریسک**: ۵ رفتاری را که خرابی‌شان بیشترین ضرر را دارد فهرست کن (پرداخت، احراز هویت، محاسبهٔ قیمت، ذخیرهٔ داده، مسیر اصلی کاربر). تست از این‌ها شروع می‌شود.
2. **لایه را درست انتخاب کن**:
   - **Unit** (اکثریت): منطق خالص — محاسبه، تبدیل داده، اعتبارسنجی. بدون شبکه/دیسک، زیر ۵۰ms.
   - **Integration**: مرز واقعی — دیتابیس آزمایشی، API handler با request واقعی. mock فقط برای سرویس خارجی.
   - **E2E** (کم و حیاتی): ۳ تا ۵ مسیر طلایی کاربر با Playwright.
3. **هر تست = یک رفتار**: نام تست جملهٔ رفتار است («قیمت با کد تخفیف منقضی تغییر نمی‌کند»). الگوی Arrange–Act–Assert.
4. **حالت‌های مرزی را عمداً بنویس**: خالی، یک عضو، حداکثر، ورودی فارسی/عربی، تاریخ جلالی، timezone، خطای شبکه، درخواست تکراری.
5. **TDD برای باگ**: هر باگ اول یک تست قرمز می‌گیرد، بعد اصلاح.
6. **پایداری**: بدون `sleep` ثابت (منتظر شرط بمان)، بدون وابستگی به ترتیب تست‌ها، داده و زمان قابل‌کنترل (fake timers، seed ثابت).
7. **CI**: تست‌های سریع روی هر PR؛ e2e روی مسیر اصلی؛ شکست باید پیام روشن بدهد.

## ضدالگوها
- تست که پیاده‌سازی را تکرار می‌کند (mock همه‌چیز) و با refactor می‌شکند.
- snapshot بزرگی که کسی بازبینی نمی‌کند.
- skip کردن تست قرمز به‌جای ریشه‌یابی.

## چک‌لیست کیفیت
- [ ] ۵ ریسک اصلی هرکدام حداقل یک تست دارند
- [ ] تست‌های unit بدون شبکه و زیر چند ثانیه کل اجرا می‌شوند
- [ ] حالت‌های مرزی (خالی، فارسی، زمان) پوشش داده شده‌اند
- [ ] هیچ تستی به ترتیب اجرا یا ساعت سیستم وابسته نیست

## خروجی
نقشهٔ ریسک + فهرست تست‌ها به تفکیک لایه + کد تست‌های اولویت‌دار + دستور اجرای محلی و CI.
