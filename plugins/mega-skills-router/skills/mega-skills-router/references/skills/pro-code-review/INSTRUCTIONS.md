# pro-code-review

## هدف
پیدا کردن ایرادهایی که واقعاً در production خراب می‌شوند، نه سلیقه‌ای. هر یافته باید یک مسیر قابل‌بازتولید از ورودی واقعی تا خرابی داشته باشد.

## چه زمانی فعال شود
«این PR رو ریویو کن»، «کدم مشکل داره؟»، قبل از merge، بعد از یک refactor بزرگ، یا وقتی تست‌ها سبزند ولی اعتماد نیست.

## گردش کار
1. **دامنه را بفهم**: هدف تغییر را از عنوان/توضیح PR یا پیام commit در یک جمله بنویس. diff را با `git diff <base>...HEAD` بگیر، نه حدس.
2. **از رفتار شروع کن، نه از ظاهر**: برای هر تابع تغییرکرده بپرس «چه ورودی‌ای این را می‌شکند؟» — مقدار خالی/null، رشتهٔ فارسی با نیم‌فاصله، عدد منفی/صفر، لیست خالی، همزمانی دو درخواست، شبکهٔ قطع.
3. **محورهای اجباری** (به این ترتیب):
   - **Correctness**: منطق شرط‌ها (off-by-one، `<` به‌جای `<=`)، مسیرهای خطا که بی‌صدا شکست می‌خورند (`catch {}` خالی)، await فراموش‌شده، mutate کردن ورودی مشترک.
   - **امنیت**: ورودی کاربر بدون اعتبارسنجی به SQL/shell/HTML/path، authz روی هر endpoint (نه فقط authn)، راز در کد/لاگ، CORS/CSRF، وابستگی ناامن.
   - **داده و مهاجرت**: migration بدون backfill یا rollback، تغییر schema که کلاینت قدیمی را می‌شکند.
   - **کارایی**: کوئری داخل حلقه (N+1)، بارگذاری کل جدول، re-render بی‌دلیل، کار سنگین در مسیر داغ.
   - **تست**: آیا تستی هست که بدون این تغییر شکست بخورد؟ اگر نه، باگ برمی‌گردد.
   - **خوانایی و هم‌خوانی**: نام‌گذاری و الگوها مثل کد اطراف باشد؛ پیچیدگی اضافه بدون دلیل.
4. **هر یافته را اثبات کن**: مسیر را از caller واقعی دنبال کن. اگر نتوانستی ورودی واقعی بسازی، آن را «احتمالی» علامت بزن، نه «باگ».
5. **شدت‌بندی**: 🔴 مسدودکننده (داده خراب/امنیت/crash)، 🟠 مهم (رفتار غلط در حالت مرزی)، 🟡 پیشنهاد (خوانایی/سبک). فقط 🔴 و 🟠 جلوی merge را می‌گیرند.
6. **راه‌حل بده**: برای هر 🔴/🟠 اصلاح مینیمال پیشنهاد کن (چند خط کد یا تست)، نه بازنویسی.

## ضدالگوها
- ده‌ها یافتهٔ سبکی که یافتهٔ واقعی را گم می‌کند.
- «شاید بهتر باشه…» بدون دلیل قابل‌اثبات.
- بازبینی فقط diff بدون خواندن caller و callee.

## چک‌لیست کیفیت
- [ ] هر یافتهٔ 🔴/🟠 فایل:خط، سناریوی خرابی و اصلاح پیشنهادی دارد
- [ ] امنیت و authz صراحتاً بررسی شده (حتی اگر «موردی نبود»)
- [ ] برای هر باگ، تستی که آن را قفل کند پیشنهاد شده
- [ ] یافته‌ها از شدیدترین به خفیف‌ترین مرتب‌اند

## خروجی
جدول یافته‌ها (شدت | فایل:خط | مشکل | سناریوی خرابی | اصلاح) + یک خط حکم: «قابل merge» / «بعد از رفع 🔴».
