# ارزیابی index و مسیریابی PSK (مرحلهٔ ۳ نقشهٔ ۹۰ روزه)

این سند بررسی مسیر تولید و بارگذاری index، اندازه‌گیری قبل و بعد، تصمیم‌ها و روش برگشت را ثبت می‌کند. محدودهٔ تغییر فقط `psk/` است.

## ۱. وضعیت پیش از تغییر

| بخش | واقعیت در `main` (fbdecf96) |
|---|---|
| registry | `data/skills-registry.json` (۳٬۰۰۰ مهارت، ۱۵٬۰۰۰ trigger). **ایستا و commit‌شده**؛ هیچ اسکریپت PSK آن را نمی‌سازد. |
| محتوای مهارت | ۳٬۰۰۰ فایل `SKILL.md` در `data/skills/` با تأیید SHA-256 (۲٬۹۹۰ مطابق، ۱۰ تعمیرشده با allowlist). |
| index | ساختار in-memory در `loadRegistry()`: نقشهٔ `term → []record` و `idf`. **فایل index وجود ندارد** و persist نمی‌شود. |
| زمان ساخت index | در هر cold start یک‌بار (`api/_core.mjs` در سطح ماژول). |
| مسیریابی | `routeSkills()` برای هر درخواست؛ کاندیدها از نقشهٔ index و امتیاز هر کاندید. |

### گلوگاه‌های شناسایی‌شده (پروفایل CPU روی مسیریابی)
1. **حلقهٔ امتیازدهی:** برای هر کاندید، `normalize(r.name)` و `tokens(r.name)` دوباره محاسبه می‌شد. این مقادیر فقط به مهارت وابسته‌اند و ثابت‌اند. بیشترین زمان مسیریابی همین‌جا بود.
2. **بارگذاری (cold start):** حدود ۳۷۰ ms. تقریباً ۹۰ ms آن توکن‌بندی trigger‌ها برای ساخت index است (اندازه‌گیری جداگانه با پروب موقت، نه در benchmark کامیت‌شده). بقیه خواندن ۳٬۰۰۰ فایل، realpath/stat، sha256 و JIT است.

## ۲. روش اندازه‌گیری

- اسکریپت: `psk/scripts/bench-routing.mjs` (بدون شبکه، بدون نوشتن فایل، خروجی JSON).
- اجرا: `npm run bench:routing -- --label=<برچسب>`
- محیط: Node **v22.22.3**، Linux x64، Intel Xeon 2.60 GHz، ۲ هسته، ۳.۸ GiB RAM (sandbox). Node 20 آزمایش نشده است.
- ورودی ثابت: `tests/fixtures/routing-corpus.json` با **۱۰۸ درخواست** (۴۰ فارسی، ۴۰ انگلیسی، ۲۰ ترکیبی، ۸ لبه‌ای).
- بارگذاری: ۳ گرم‌کردن + ۱۵ اندازه‌گیری.
- مسیریابی: ۳ گرم‌کردن + ۵۰ دور؛ هر فراخوانی جداگانه با `process.hrtime.bigint` زمان‌سنجی می‌شود.
- handler: `GET /api/skills` با یک درخواست سنگین، ۳ گرم‌کردن + ۵۰ اندازه‌گیری، با telemetry خاموش و روشن.
- `outputDigest`: SHA-256 روی کل خروجی `routeSkills` برای ۱۰۸ مورد. برابری آن یعنی ترتیب، امتیاز، توکن‌ها و وضعیت محتوا تغییری نکرده‌اند.
- روش مقایسه: نسخهٔ `main` در پوشهٔ موقت (`git archive`) با **همان** اسکریپت و همان corpus اجرا شد؛ اجراها متناوب و سه‌بار تکرار شد.

## ۳. نتایج (میانهٔ p50؛ سه اجرای مستقل)

| شاخص | `main` (fbdecf96) | شاخهٔ کاری | تغییر |
|---|---|---|---|
| بارگذاری/index (cold start) | 370–380 ms | 397–404 ms | **+≈25 ms** (≈+6٪) |
| مسیریابی هر دور (۱۰۸ درخواست) | 138–144 ms | 45–47 ms | **≈۳ برابر سریع‌تر** |
| هر فراخوانی مسیریابی p50 | 989–1031 µs | 310–327 µs | ≈−68٪ |
| هر فراخوانی مسیریابی p95 | 3576–3733 µs | 1258–1293 µs | ≈−65٪ |
| handler `GET /api/skills` (telemetry خاموش) | 3.44–3.59 ms | 1.14–1.20 ms | ≈−66٪ |
| handler با telemetry روشن | — | 1.13–1.21 ms | در حد نویز نسبت به خاموش |
| `outputDigest` | `sha256:3745f143…` | `sha256:3745f143…` | **یکسان در همهٔ اجراها** |

**تفسیر:** مسیریابی هر درخواست حدود ۰.۸۶ ms سریع‌تر شده و هزینهٔ اضافهٔ cold start حدود ۲۵ ms است. بنابراین از حدود ۳۰ درخواست در هر instance به بعد سود خالص دارد. این عدد برای یک ماشین sandbox است و در Vercel اندازه‌گیری نشده است.

## ۴. تصمیم‌ها

### تغییر انجام‌شده (محدود و قابل‌اندازه‌گیری)
- نام هر مهارت (`normalize` و توکن‌های نام) یک‌بار در `loadRegistry()` محاسبه و روی record ذخیره می‌شود (`nameNorm`، `nameTokens`)؛ `routeSkills()` دیگر آن را برای هر کاندید بازمحاسبه نمی‌کند.
- ترتیب حلقه‌ها، فرمول امتیاز و همهٔ قراردادها بدون تغییر است؛ digest خروجی یکسان است.

### انجام نشده و دلیل آن
- **artifact index از پیش‌ساخته:** شواهد فعلی نیاز به آن را نشان نداد. ذخیرهٔ index فقط حدود ۹۰ ms از cold start را حذف می‌کند (سقف تخمینی) و خواندن فایل‌ها و sha256 را حذف نمی‌کند، چون اعتبارسنجی SHA-256 باید باقی بماند. در مقابل، نیاز به نسخهٔ tokenizer، تشخیص artifact قدیمی/خراب و بازسازی امن دارد. هزینه/فایده کافی نیست؛ اگر cold start در ترافیک واقعی گلوگاه شد، این گزینه دوباره ارزیابی می‌شود.
- **hoist کردن regexهای ثابت** داخل حلقهٔ کاندیدها: پروفایل سهم کمی را نشان داد؛ تغییر نشد تا diff بی‌دلیل بزرگ نشود.
- **تغییر API، فرمت پاسخ، tokenization یا اعتبارسنجی SHA-256:** انجام نشد.

## ۵. تست‌های قرارداد

- `tests/routing-contract.test.mjs` خروجی کامل `routeSkills` را برای ۱۰۸ درخواست با `tests/fixtures/routing-golden.json` **دقیقاً** مقایسه می‌کند (`deepStrictEqual`). golden از کد `main` ساخته شد؛ پس هر تغییر ناخواستهٔ ترتیب یا امتیاز شکست می‌خورد.
- بررسی mutation: تغییر وزن ۰.۱۲ به ۰.۱۲۱ در یک جملهٔ امتیازدهی باعث شکست تست شد؛ فایل بازگردانده شد.
- invariantها: ترتیب نتایج (امتیاز، سپس تعداد trigger، سپس نام)، سقف `limit` (۱ تا ۲۵)، و صفر نتیجه برای درخواست‌های فقط stop-word.
- به‌روزرسانی golden فقط با `npm run routing:golden` در حالت `--write` و با بازبینی دستی مجاز است.

## ۶. ریسک‌ها و محدودیت‌ها

- benchmark روی sandbox اجرا شده و نتیجهٔ production نیست. زمان واقعی Vercel (CPU، memory و شبکه) متفاوت است و اندازه‌گیری نشده است.
- هزینهٔ cold start از ~۳۷۰ ms به ~۴۰۰ ms رفته است. هنوز زیر سقف ۶۰ ثانیه‌ای تابع است.
- Node 22 آزمایش شد؛ `engines` پروژه `>=20` است و Node 20 تست نشده است.

## ۷. بازگشت به نسخهٔ قبل (rollback)

- اگر مشکلی در مسیریابی دیده شد: revert همین PR. تغییر router فقط در `engine/router.mjs` است (دو فیلد جدید روی record در بارگذاری و حذف محاسبهٔ تکراری نام در حلقهٔ امتیازدهی)؛ هیچ داده یا artifact persist ندارد.
- golden و تست‌ها با revert برمی‌گردند؛ هیچ migration یا تنظیم Vercel وجود ندارد.
