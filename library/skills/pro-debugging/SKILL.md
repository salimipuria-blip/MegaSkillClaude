# pro-debugging

## هدف
رسیدن به **علت ریشه‌ای** با شواهد، نه وصله روی علامت. «flaky» و «مشکل شبکه» علت نیستند تا اثبات شوند.

## چه زمانی فعال شود
خطا، stack trace، تست قرمز، رفتار غلط، کندی، «دیروز کار می‌کرد»، یا شکست گاه‌به‌گاه.

## گردش کار
1. **بازتولید کن**: کوچک‌ترین دستوری که خطا را نشان می‌دهد پیدا کن و دقیق ثبت کن (دستور، ورودی، نسخه‌ها، محیط). بدون بازتولید، هر «اصلاح» حدس است.
2. **پیام خطا را کامل بخوان**: پایین‌ترین فریم stack که در کد خود پروژه است، نوع خطا، و مقدار واقعی متغیرها. خطای اول مهم است، نه آخرین.
3. **فضای جست‌وجو را نصف کن**:
   - «دیروز کار می‌کرد» → `git bisect` بین commit سالم و خراب.
   - در کد → لاگ/breakpoint وسط مسیر داده؛ ببین داده کجا از درست به غلط تبدیل می‌شود.
   - در محیط → همان کد را در محیط تمیز (container، نسخهٔ قفل‌شدهٔ وابستگی) اجرا کن.
4. **فرضیه بنویس و تست کن**: «اگر علت X است، آن‌وقت Y باید درست باشد» — Y را بسنج. هر بار یک متغیر را عوض کن.
5. **علت را توضیح بده**: یک جمله که همهٔ علائم را توضیح دهد. اگر علامتی توضیح داده نمی‌شود، هنوز تمام نشده.
6. **اصلاح مینیمال + تست regression**: اول تستی بنویس که با کد فعلی شکست بخورد، بعد اصلاح کن تا سبز شود. تست را نگه دار.
7. **همسایه‌ها را بگرد**: همان الگوی باگ معمولاً جای دیگری هم هست (`grep`).

## الگوهای رایج علت
- همزمانی/race: ترتیب await، state مشترک، cache قدیمی.
- مرز داده: null/undefined، رشتهٔ خالی، timezone و تقویم جلالی، encoding فارسی (ی/ي، ک/ك، ZWNJ).
- محیط: متغیر محیطی گم، نسخهٔ متفاوت Node/Python، تفاوت lockfile، proxy.
- شکست بی‌صدا: catch خالی، promise بدون await، خطایی که لاگ نمی‌شود.

## چک‌لیست کیفیت
- [ ] دستور بازتولید دقیق ثبت شده
- [ ] علت ریشه‌ای در یک جمله، با شاهد (لاگ/مقدار/commit)
- [ ] تست regression که قبل از اصلاح قرمز و بعد سبز است
- [ ] هیچ تستی skip یا حذف نشده تا سبز شود

## خروجی
گزارش کوتاه: علامت → بازتولید → علت ریشه‌ای (با شاهد) → اصلاح → تست regression → جاهای مشابه بررسی‌شده.
