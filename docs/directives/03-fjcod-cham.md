# 03 — CHAM Store OS (`fjcod/`)

## مأموریت و مرزها
سامانهٔ مدیریت فروشگاه چام (React 19 + TypeScript + Vite): فروش، موجودی، مشاوران و صندوق. تا قبل از مهاجرت بک‌اند، **نسخهٔ فعلی محلی و برای دادهٔ واقعی/مالی امن نیست و نباید به‌عنوان سامانهٔ مالی چنددستگاهی معرفی شود.**

## وضعیت فعلی (شواهد: `fjcod/README.md`, `docs/security/SUPABASE_RLS_PLAN.md`, `docs/REPO_HARDENING.md`)
- ✅ فرانت کامل با `npm run check` سبز (typecheck + vitest + build) و e2e مرورگر (`npm run e2e`).
- ⚠️ **بدهی بحرانی:** بک‌اند و احراز هویت سروری ندارد؛ داده در مرورگر هر دستگاه است (پاک‌شدن حافظه = از دست رفتن فروش)؛ رمزهای اولیهٔ پیش‌فرض در مستندات/کد توزیع شده‌اند و مجوزها سمت کلاینت قابل دستکاری‌اند.
- آمادهٔ بازبینی ولی **اعمال‌نشده**: migration اسکیما/RLS در `supabase/migrations/20261014000000_cham_schema_rls.sql` (۱۱۵ statement، فقط parse شده؛ روی هیچ دیتابیسی اجرا نشده، RPC تراکنشی ندارد، seed ندارد).
- انتشار زنده هنوز از مخزن قدیمی `FJCod` انجام می‌شود، نه از اینجا.

## معماری و فایل‌های کلیدی
`src/{App.tsx,pages,components,core,lib}` (منطق فروش/موجودی در `core`، نشست موقت در `lib`)، `tests/{auth-session,core,store}.test.ts`، `supabase/config.toml` + `supabase/migrations/`، طرح مهاجرت در `docs/security/SUPABASE_RLS_PLAN.md`.

## اجرا و تست
```bash
cd fjcod && npm ci && npm run check     # = typecheck + vitest + build (هر سه الزامی)
npm run build && npm run e2e            # smoke مرورگر
npx tsc -b --pretty false               # ایزوله‌کردن خطای تایپ
```

## پروتکل دیباگ حرفه‌ای
- **باگ فروش/موجودی:** اول تست واحد `core` برای همان سناریو بنویس (قرمز)، بعد اصلاح (سبز)؛ محاسبات پول با عدد صحیح (ریال/تومان صریح) — خطای اعشار را با `toFixed` نپوشان.
- **مشکل نشست:** محافظ فعلی عمداً موقت است (هر refresh = ورود مجدد)؛ «رفع» آن با برگرداندن اعتماد به `sessionStorage` رگرسیون امنیتی است و ممنوع. مسیر درست فقط Auth سروری است.
- **از دست رفتن داده:** از «سیستم و مجوز» بک‌آپ بگیر و restore را روی مرورگر دوم تست کن؛ هرگز برای دیباگ، دادهٔ واقعی کاربر را پاک/جایگزین نکن.
- **خطای Build:** `tsc -b` را از Vite جدا کن؛ خطای تایپ را با `any` خاموش نکن.

## راه‌حل مهاجرت بک‌اند (P0 — ترتیب اجرا الزامی)
1. اتصال Vercel به همین مخزن (Root Directory=`fjcod`) تا کد و انتشار یکی شود.
2. ساخت پروژهٔ Supabase و اعمال migration بازبینی‌شده؛ نگاشت کاربران محلی → حساب واقعی Auth؛ **حذف و چرخش همهٔ رمزهای پیش‌فرض منتشرشده**.
3. RLS بر اساس نقش (مالک/مدیر/معاون/صندوقدار/مشاور) + RPC تراکنشی برای فروش و کسر موجودی (اتمیک، idempotent با کلید یکتای درخواست).
4. مهاجرت داده با بک‌آپ قابل‌بازگشت؛ تست دودستگاهی، کاربر غیرمجاز (RLS)، ریست مرورگر و restore پشتیبان.
5. حالت آفلاین: صف عملیات (outbox) با همگام‌سازی و حل تعارض مستند، نه حدسی.

## گسترش بعدی
- **P1:** ورود گروهی کالا از اکسل، چاپ برچسب بارکد، گزارش اختلاف صندوق (هدف < ۰٫۵٪).
- **P2 (محصول FJCOD):** چندمستأجری، کنسول اشتراک، اتصال کارتخوان و سامانهٔ مؤدیان — فقط بعد از بک‌اند امن.

`npm run check` و e2e سبز؛ هر تغییر سمت داده: تست RLS برای نقش مجاز/غیرمجاز؛ هیچ رمز پیش‌فرضی در کد/README نماند؛ وضعیت مهاجرت در `docs/REPO_HARDENING.md` صادقانه به‌روز شود.
